# Create or Modify System Process

**Technique ID:** T1543
**Tactic:** Persistence, Privilege Escalation

## Description
Adversaries may create or modify system-level processes to repeatedly execute malicious payloads as part of persistence. This includes creating or modifying Windows Services, Linux systemd services, or macOS launch daemons.

## Attacker Behavior
Attackers use tools like `sc.exe` to install a new Windows service that executes a malicious binary under the `NT AUTHORITY\SYSTEM` account. Alternatively, they might modify the binary path of an existing, benign service (Service Execution Hijacking) to point to malware.

## SOC Evidence
- Execution of `sc.exe create` or `sc.exe config`.
- Windows Security Event ID 4697 (A service was installed in the system) or Event ID 7045 (Service Creation).
- Creation of new `.service` files in `/etc/systemd/system/`.

## Detection Clues
Monitor for the creation of services launching binaries from temporary, public, or user profile directories. Pay attention to services created with suspicious names, typosquatted names, or those executing command interpreters.

## Related Techniques
- T1574: Hijack Execution Flow
- T1569: System Services

## Example Alert Context
A Sysmon Event ID 1 alert shows `sc.exe` being executed to modify the `binPath` of the "Spooler" service to execute `C:\Windows\Temp\malware.exe`.

## Wazuh Relevance
Wazuh natively parses Windows Event logs (like 4697 and 7045) and can trigger alerts when new services are installed. FIM can also detect the creation of Linux systemd unit files.

## Suricata Relevance
Suricata will not detect the modification of a system process directly. It can only detect subsequent network activity generated by the newly established service.

## Investigation Guidance
Identify the exact binary path executed by the new or modified service. Revert any modifications to legitimate services to their original state. Check for lateral movement tools (like PsExec) which inherently create temporary Windows services during execution.

# Abuse Elevation Control Mechanism

**Technique ID:** T1548
**Tactic:** Privilege Escalation, Defense Evasion

## Description
Adversaries may circumvent mechanisms designed to control elevate privileges to gain higher-level permissions. This includes bypassing User Account Control (UAC) on Windows or exploiting `sudo` misconfigurations on Linux.

## Attacker Behavior
Attackers execute specialized payloads that exploit UAC bypass techniques (such as COM handler hijacking or mock trusted directories) to launch elevated processes without prompting the user. On Linux, they might exploit wildly permissive `sudoers` configurations.

## SOC Evidence
- Process creation events showing a high-integrity process spawning from a medium-integrity process without a valid UAC prompt (Event ID 4624 Logon Type 9).
- Use of known UAC bypass tools like UACMe.
- Changes to registry keys associated with COM handlers (e.g., `HKCU\Software\Classes\mscfile\shell\open\command`).

## Detection Clues
Monitor for unusual registry modifications under `HKCU\Software\Classes`. Look for unexpected instances of `dllhost.exe`, `sdclt.exe`, or `eventvwr.exe` spawning command prompts or PowerShell.

## Related Techniques
- T1055: Process Injection
- T1078: Valid Accounts

## Example Alert Context
A Wazuh alert detects `eventvwr.exe` launching `cmd.exe` running as Administrator, a classic UAC bypass indicator.

## Wazuh Relevance
Wazuh monitors process lineage and registry modifications. Rules can identify known UAC bypass techniques by correlating the execution of specific Windows binaries with sudden integrity level changes.

## Suricata Relevance
Suricata cannot detect local privilege escalation or UAC bypasses directly.

## Investigation Guidance
Investigate the initial vector that delivered the UAC bypass payload. Assess what actions the attacker performed once they gained SYSTEM or elevated Administrator privileges. Ensure systems are patched and UAC is configured to "Always Notify".
